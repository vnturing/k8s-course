Kubernetes on Incus / Lesson 2

Four Incus VMs

About 20 minutes · hands-on · needs Lesson 1 · commands saved in the Incus cheat sheet

By the end, incus list shows four running virtual machines: one server and three agents, ready for k3s.

Why VMs, not containers

Incus can launch system containers or virtual machines from the same image; adding --vm makes it a VM (Incus: create instances). A container shares your laptop’s kernel; a VM boots its own. Kubernetes nodes want their own kernel, so we use VMs.

Step 0 · Preflight

incus --version
ls -l /dev/kvm            # VMs need hardware virtualisation
incus admin init --minimal   # only if you never initialised Incus
systemctl is-active docker   # if “active”, read the troubleshooting section below first

The --minimal flag applies a basic automatic configuration (Incus: first steps). If you get a permission error, your user probably isn’t in the incus-admin group; check your Incus install notes. Tell me what you see and we’ll sort it out.

Step 1 · Launch the server

incus launch images:debian/13 k3s-server --vm \
  -c limits.cpu=2 -c limits.memory=3GiB

This is the documented form for a VM with CPU and memory limits (incus launch). The first launch downloads the image, so it takes longer.

Step 2 · Launch three agents

for i in 1 2 3; do
  incus launch images:debian/13 k3s-agent$i --vm \
    -c limits.cpu=2 -c limits.memory=2GiB
done

The VM name becomes its hostname, which matters: k3s requires that no two nodes share a hostname (k3s requirements).

Step 3 · Look at what you made

incus list
incus exec k3s-server -- free -m

VMs need a minute to boot before an IPv4 address appears. Re-run incus list until all four have one. free -m inside the server should show roughly 3 GiB, not your laptop’s 16 (the Incus tutorial runs this same comparison for containers: first steps).

Optional: find the server’s address with incus list k3s-server -c n4, then from an agent run incus exec k3s-agent1 -- ping -c3 <server-ip>. Ping the server, not another agent, so you know which address you tested. If ping is missing, install it with apt-get install -y iputils-ping inside the VM. This confirms the VMs can reach each other, which k3s will rely on.

If the VMs can’t reach each other

A failed ping between VMs, while pinging the gateway (the bridge’s own address, e.g. 10.225.16.1) works, points at the host’s firewall. Incus’s firewall guide says running Incus and Docker on the same host can cause connectivity issues, commonly because Docker sets the FORWARD policy to drop. Check: 

systemctl is-active docker
sudo iptables -S FORWARD | head -3   # look for -P FORWARD DROP
lsmod | grep br_netfilter

To test the theory (these rules vanish on reboot), allow traffic on the Incus bridge, replacing incusbr0 with your bridge name from incus network list:

sudo iptables -I DOCKER-USER -i incusbr0 -j ACCEPT
sudo iptables -I DOCKER-USER -o incusbr0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

If that fixes it, pick a lasting fix. The Incus docs’ easiest is to remove Docker from the host and run it inside a VM if you need it, then reboot. If Docker must stay, they point to Docker’s ip-forward-no-drop option. Also confirm no old Kubernetes install is running on the host (systemctl is-active k3s); a leftover one competes for memory and adds firewall rules.

Worth writing up

This failure is a good blog section on its own: symptom, the gateway-vs-VM test that narrowed it, the firewall cause, the fix. Debugging narratives are what interviewers ask about.

Retrieval practice

Which flag makes incus launch create a virtual machine?

  1. --kvm
  2. --vm
  3. --machine
  4. --virtual

Without --vm, Incus launches a container sharing the host kernel.

Why do the four VMs get different names?

  1. Every node needs a unique hostname
  2. Every node needs a shared hostname
  3. Every node needs a numeric hostname
  4. Every node needs a fully-qualified hostname

k3s requires unique hostnames; the VM name becomes the node’s hostname.
