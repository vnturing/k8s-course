Kubernetes on Incus / Lesson 3

Your Compose file, through Kubernetes eyes

About 20 minutes · no cluster needed · can be done before or after Lesson 2

By the end you can take one service from your homelab docker-compose.yml and say which Kubernetes objects it becomes, and what gets lost on the way.

You already know half of this

You declare services in Compose and let Docker make reality match. Kubernetes works the same way at a larger scale: you declare objects, and the cluster keeps working until reality matches. The new part is the vocabulary, so we’ll borrow the translation Kubernetes itself documents.

The Kubernetes docs describe Kompose, a conversion tool from Compose to Kubernetes (Translate a Docker Compose File to Kubernetes Resources). Its default output is a set of Deployments and Services as YAML files (same guide, v1.33). You’ll use it as a dictionary, not as a migration tool.

The translation table

In ComposeKompose producesEvidence
A service (image, environment)A …-deployment.yamluser guide’s sample output
ports:A Service file, e.g. web-tcp-service.yamltask page
volumes:A …-persistentvolumeclaim.yamlsample output in the user guide
build:Nothing: a warning, “Unsupported key build - ignoring”user guide

The last row is the interesting one. A cluster pulls images; it doesn’t run your build: step. So in Kubernetes, building and publishing an image becomes a separate job, which is exactly the sort of thing platform and CI work is about. We’ll return to it.

What’s not in this table: depends_on, restart policies, networks, healthchecks. I haven’t verified how Kompose or Kubernetes handles them, so we’ll learn each from the docs when we reach it rather than guess now.

Try it on your own file

Pick your simplest homelab service. Install Kompose using the official guide (check the releases page for the current version, since the guide’s example URL shows v1.34.0). Then, in a scratch directory:

cp ~/path/to/docker-compose.yml .
kompose convert
ls

Converting needs no cluster. Applying the output with kubectl apply does, and you shouldn’t do that yet. Open the generated Deployment and Service files and find: where your image went, where your port went, and what you wrote in Compose that has no visible counterpart.

Retrieval practice

A Compose service with a published port becomes which pair?

  1. DaemonSet plus Volume
  2. Ingress plus ConfigMap
  3. Deployment plus Service
  4. StatefulSet plus Secret

Kompose’s default output is Deployments and Services.

What does Kompose do with a Compose build: key?

  1. It builds the image first
  2. It pushes the image upstream
  3. It emits a Dockerfile instead
  4. It ignores the key, warning

It warns “Unsupported key build - ignoring”. Kubernetes needs a ready-made image it can pull.

Compose volumes: became which object in Kompose’s sample?

  1. A ConfigMap
  2. A PersistentVolumeClaim
  3. A DaemonSet
  4. An Ingress

The sample output included a …-persistentvolumeclaim.yaml file for the database’s volume.

Publish it

Blog angle: “What my homelab Compose file looks like to Kubernetes.” Show one service side by side with its generated files, and list what didn’t carry over. A post that admits its gaps reads as honest, which helps in interviews.
Say it aloud: “A Compose service roughly maps to a Deployment plus a Service; volumes become claims; build doesn’t carry over, so images need a registry.”
